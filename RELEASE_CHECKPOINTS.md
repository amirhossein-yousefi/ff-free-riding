# Checkpoint release

This document lists the 106 checkpoint files of the release for the paper *Cumulative-Goodness Free-Riding in Forward-Forward Networks: Real, Repairable, but Not Accuracy-Dominant* (NeurIPS 2026): the `stage1_best.pt` and `stage2_best.pt` of 53 of the paper's runs, with their source, lineage, size and SHA-256. It does not cover every run the paper reports ([Not covered by the release](#not-covered-by-the-release)). The machine-readable version is [`release_manifest.json`](release_manifest.json). Each of its entries has an `availability` field, and `_meta.subsets` defines the public, minimal and full subsets.

The public release on the Hugging Face Hub (<https://huggingface.co/Amirhossein75/ff-free-riding>) holds 29 of the 106 files: the validation-selected Stage-1 network (`stage1_best.pt`) of every run of the CIFAR-100 trio and MGC arms, the CIFAR-10 squared-hinge, MGC-D128 and CP-FAIR runs, the Tiny ImageNet γ=0 runs and the CIFAR-10 NoMem-L2 run. The first release (2026-10-01, subset `minimal`) held 4 of them: the seed-42 files of the four central CIFAR-100 arms of main-text Table 3. The other 77 files are available from the author on request (amir.usefi75@gmail.com). Their SHA-256 values below let a recipient verify them. This document also gives the commands used to stage and upload the public release.

- **Size:** 29 files, 14,291,136,349 bytes (14.3 GB).
- **Columns:** the epoch is the file's `epoch_stage1`, and the validation top-1 is its `best_s1`: the S1 readout with flip TTA on the run's held-out validation split, which selected the checkpoint. S1 and S1-TTA are the test top-1 (%) that the run logged in its final evaluation; for Tiny ImageNet the test set is the labeled validation split.
- **What they give:**
  - S1 and S1-TTA are the Stage-1 readouts of these files: the goodness-sum readout of the EMA weights on a single crop, and with a horizontal flip added.
  - The paper prints these per-seed values in Table 5 (MGC), Table 21 (CP-FAIR), Table 25 (Tiny ImageNet; S1 in its caption) and Table 27 (NoMem-L2). For the CIFAR-100 trio it prints the per-seed S1 in Table 36 (seed 42 also in Table 9) and S1-TTA only as 3-seed means (Table 3). For the squared hinge it prints 3-seed means (Table 7). The per-seed values are in [`metric_summaries/camera_ready/`](metric_summaries/camera_ready/).
  - The CIFAR-100 backbones also give the frozen-backbone readouts and probes of Tables 9–11. Tables 13 (`tab:early_exit`) and 36 (`tab:e1_aligned`) were computed by re-scoring the trio files, and Table 36 also the CP-FAIR files.
  - The deepest-block separation of Tables 3, 5 and 7 is a training-log value (last Stage-1 epoch), not a checkpoint quantity. Table 36 (`tab:e1_aligned`) recomputes it on the validation-selected trio and CP-FAIR checkpoints (EMA weights, eval mode).
- **Stage 2:** the Stage-2 heads (`stage2_best.pt`) of all 53 runs are available on request, not public. Retrain the Stage-2 probe from a public Stage-1 file ([below](#retraining-the-stage-2-probe)) or ask for the original heads. For NoMem-L2 the paper prints no Stage-2 value of its own: its S2-TTA enters the Stage-2 summary of App. N (`sec:secondary_analysis`), taken over the 12 seed-42 variants of Table 27 that were run through Stage 2.
- **Checks before upload** (2026-10-24, CPU; recorded per file in `release_manifest.json` as `lineage_check` and `loading_spot_check`):
  - Each file's SHA-256, size and CRC-32 equal the manifest. The extracted trio copies have the same CRC-32 and size as their Google Drive archive members, and the Tiny ImageNet files are streamed from their archive members, whose CRC-32 zipfile verifies on read.
  - The result-bearing run's `events.jsonl` names the file in its final test evaluation, and the logged S1/S1-TTA equal the per-seed values behind the paper's tables (`lineage_check`).
  - The stored `best_s1` equals the run's `run_end.best_s1`, and the stored `cfg` equals the run's `config.json`, apart from `device`.
  - Every file loads with `torch.load(..., weights_only=True)` (PyTorch 2.14.0). Its `net_ema` loads into its group's camera-ready trainer with every key matched, and every key of its stored `cfg` is a field of that trainer's `FFConfig`.
  - The model card's loading code, run on CPU in float32, gives the same single-crop prediction as the run's own saved test predictions (`preds_stage1_test_no_tta.npz`) for 1,854 of 1,856 file–image pairs: each of the 29 public files scored the first 64 images of its test set (`loading_spot_check`). The dense files agree on 960 of 960, with every per-class score within 0.03 of the saved one. The MoE files (`mgc_d128`, `hinge`, `c10_cp_fair`, `c10_nomem_l2`) agree on 894 of 896, with every per-class score within 1.15 of the saved one. The original evaluations ran on GPUs with TF32; see the model card's precision note.
- **Model card:** [`release/MODEL_CARD.md`](release/MODEL_CARD.md), which also gives the trainer and test-set normalization of each group and a loading snippet.

- **Scope:** every other row of the [file list](#file-list), marked "on request": 77 files, 46.31 GB. These are:

  - the Stage-1 networks of the 24 CIFAR-10 γ=0, gated-ablation and hardness-gated κ=0 runs.
- **How to ask:** email the author (amir.usefi75@gmail.com).
- **How they are shared:** `release/stage_release.py --subset full` stages them with the same layout and writes `SHA256SUMS`.
- **All files:** 106 checkpoints, 60.60 GB in total (29 public, 77 on request).
- **Per run:**
  - `stage1_best.pt` is the validation-selected Stage-1 network, including the EMA weights that give the S1 and S1-TTA numbers.
  - `stage2_best.pt` is the Stage-1 network plus the Stage-2 head, which gives S2 and S2-TTA. It is listed for every run in the manifest.
  - The `*_last.pt` resume files are not part of the release.
- **Hashing:**
  - SHA-256 over the full file bytes (Python hashlib, 8 MiB chunks).
  - Archive members were streamed from the Google Drive export zips without extraction, and zipfile verified each member's CRC-32.
  - Extracted copies were cross-checked against their archive member's CRC-32.
- **Sources** are given relative to `FF_HOME`, the root of the run archive, which contains `amir-porjects/` and `ff-next/`. `archive.zip::member` names a member of a Google Drive export zip.
- **Loading:** `torch.load(path, map_location='cpu', weights_only=False)` (the 29 public files also load with `weights_only=True` under PyTorch 2.14.0; `weights_only=False` executes pickle code, so use it only on files whose SHA-256 matches).
  - The dict holds `model`, `net_ema`, `cfg`, the optimizer, scheduler and queue states and, for `stage2_best.pt`, `head_state`.
  - Rebuild the network with the matching trainer and the run's configuration, stored as `cfg` in the checkpoint. See the model card, or `analysis/readouts/s2ff_readout.py` for a minimal example.

## Retraining the Stage-2 probe

When a Stage-1 checkpoint is complete, the trainer skips Stage 1 and does two things:

1. It trains only the Stage-2 attentive head on the frozen EMA backbone, with the run's train/validation split, which it regenerates from the seed.
2. It runs the final test evaluation (S1, S1-TTA, S2, S2-TTA), written to `events.jsonl` of a new run directory.

This needs a GPU. Put the file under both of its trainer names in `FF_CKPT_DIR`:

- Stage 1 resumes from `<run>_stage1_last.pt`.
- Stage 2 and the final Stage-1 evaluation load `<run>_stage1_best.pt`.

Set `FF_EPOCHS_STAGE1` to the checkpoint's `epoch_stage1`. Otherwise the trainer resumes Stage-1 training. The commands below are for the four seed-42 CIFAR-100 files (362 for γ=0 and MGC, 340 for κ=0 and cumulative; 20 Stage-2 epochs). They use `hf`, the command-line tool that `pip install huggingface_hub` installs; current `huggingface_hub` releases no longer run `huggingface-cli`. The `&&` chain stops before the trainer starts if the download or a copy fails; without a checkpoint in `FF_CKPT_DIR`, the trainer would start Stage 1 from scratch.

```bash
ARM=gamma0;       EP=362; ENV="FF_GAMMA_SCALE=0"
# ARM=gated_k0;   EP=340; ENV="FF_GAMMA_GATING_MODE=adaptive FF_GAMMA_0=0.7 FF_GAMMA_KAPPA=0.0 FF_GAMMA_TAU=1.0"
# ARM=cumulative; EP=340; ENV="FF_GAMMA_SCALE=0.7"
F=ff_cifar100_cifar100_${ARM}_seed42_L4_D256_P2_seed42_stage1_best.pt
hf download Amirhossein75/ff-free-riding "checkpoints/c100_trio/$F" --local-dir ./hf && \
mkdir -p ckpt_s2 && cp "hf/checkpoints/c100_trio/$F" ckpt_s2/ && cp "ckpt_s2/$F" "ckpt_s2/${F/_best/_last}" && \
env $ENV FF_CKPT_DIR=./ckpt_s2 FF_VERSION_TAG=cifar100_${ARM}_seed42 FF_EPOCHS_STAGE1=$EP \
  FF_NUM_BLOCKS=4 FF_D_MODEL=256 FF_NUM_HEADS=8 FF_USE_SAM=0 FF_N_EXPERTS=1 FF_MOE_TOP_K=1 \
  FF_SEED=42 python trainers/cp_fair_cifar100.py

# MGC (EP=362, the default)
F=ff_cifar100_mgc_c100_L4_D256_P2_seed42_stage1_best.pt
hf download Amirhossein75/ff-free-riding "checkpoints/mgc_c100/$F" --local-dir ./hf && \
mkdir -p ckpt_s2 && cp "hf/checkpoints/mgc_c100/$F" ckpt_s2/ && cp "ckpt_s2/$F" "ckpt_s2/${F/_best/_last}" && \
FF_CKPT_DIR=./ckpt_s2 FF_VERSION_TAG=mgc_c100 FF_USE_MGC=1 FF_MGC_C0=1.0 FF_N_EXPERTS=1 FF_MOE_TOP_K=1 \
  FF_USE_SAM=0 FF_NUM_HEADS=8 FF_GAMMA_GATING_MODE=constant FF_GAMMA_SCALE=0.7 FF_EPOCHS_STAGE1=362 FF_SEED=42 \
  python trainers/cp_fair_cifar100.py
```

- **Environment:** the per-arm environment is the arm's row of [`repro_manifest.csv`](repro_manifest.csv), with `FF_EPOCHS_STAGE1` set to the selected epoch. The resulting `config.json` equals the original run's, apart from `device`, the camera-ready switches (all off) and, for κ=0 and cumulative, `epochs_stage1`. The regenerated train/validation split equals the run's saved `split_indices.json`. Both were checked on CPU up to the start of Stage 2 for these four files.
- **Other files:** use the group's trainer (model card) and the environment of the run's row in `repro_manifest.csv` (every public group except NoMem-L2 has one). Set `FF_SEED` to the run's seed, `FF_EPOCHS_STAGE1` to the file's `epoch_stage1`, and `FF_VERSION_TAG` to the part of the file name between `ff_<dataset>_` and `_L<blocks>`, so that the trainer finds the file under its run name (`ff_<dataset>_<tag>_L<blocks>_D<width>_P<patch>_seed<seed>`). These commands were not checked one by one. The trainer builds its configuration from its own defaults and these environment variables, not from the stored `cfg`, so two groups need a change in the trainer's `FFConfig`:
  - Tiny ImageNet: the runs' Stage-2 head had `head_hidden=1536`, but `trainers/cp_fair_tiny_imagenet.py` defaults to 2048 and has no environment variable for it. Set `head_hidden` to 1536 before retraining.
  - NoMem-L2 (no row): its settings are in its stored `cfg`, for example 300 Stage-2 epochs. The `cfg` predates the trainer's `block_curr_depth_slope` setting, which must be 0 for this run (a uniform current-block weight of 0.5).
- **Expected numbers:** a retrained head is not bitwise identical to the paper's. The trainers that produced these runs did not store RNG state, so the Stage-2 data order differs. Expect S2 values close to the logged ones, which are in the model card, but not equal to them.

## Staging and upload commands (for the author)

```bash
# 1. stage the 29 public files (copied, SHA-256 verified), README.md (release/MODEL_CARD.md),
#    release_manifest.json and SHA256SUMS; stage_release.py exits with status 1 and deletes the staged copy
#    if a file fails its SHA-256 check, so upload only if this whole command succeeds
export FF_HOME=/path/to/archive/root          # contains amir-porjects/ and ff-next/
python release/stage_release.py --subset public --copy --dest ./hf_release && \
  (cd hf_release && sha256sum -c SHA256SUMS) && [ "$(wc -l < hf_release/SHA256SUMS)" -eq 29 ]

# 2. upload (14.3 GB; `upload` creates the model repository if it does not exist)
hf auth login
hf upload Amirhossein75/ff-free-riding ./hf_release . --repo-type model \
  --commit-message "Checkpoint release (NeurIPS 2026)"
#    or, from Python:
#    from huggingface_hub import HfApi; api = HfApi()
#    api.create_repo("Amirhossein75/ff-free-riding", repo_type="model", exist_ok=True)
#    api.upload_folder(folder_path="hf_release", repo_id="Amirhossein75/ff-free-riding", repo_type="model")

# 3. verify the upload from a clean directory
hf download Amirhossein75/ff-free-riding --repo-type model --local-dir ./hf_check && cd hf_check && sha256sum -c SHA256SUMS
```

The commands use `hf`, the command-line tool that `pip install huggingface_hub` installs; current `huggingface_hub` releases no longer run `huggingface-cli`. On the same filesystem as the sources, leave out `--copy` and the files are hard-linked. `--subset minimal` stages the 4 files of the first release. To share on-request files, stage them with `python release/stage_release.py --subset full --dest ./full_release` (about 61 GB; `--only-group <group>` stages one group), which also copies `preds_cifar100/` to `predictions/` and adds those files to `SHA256SUMS`.
